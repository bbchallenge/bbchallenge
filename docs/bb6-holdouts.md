# BB(6) holdouts page

`/bb6` lists every machine on the current official BB(6) holdouts list, with its class, its status in
[busycoq](https://github.com/ccz181078/busycoq/tree/BB6) and links. It is a static page: there is no server and no
scheduled rebuild. Everything on it comes from `static/bb6/holdouts.json`, which is generated by scripts you run
by hand and commit. The busycoq status is refreshed in the visitor's browser (see "Live check").

## Files

| Path | What it is |
| --- | --- |
| `src/routes/(app)/bb6/+page.svelte` | The page (search, filters, sort, table, details, sources). |
| `src/lib/bb6/tm_key.js` | Machine-code parsing and the canonical key (mirror and state renaming). Shared by the page and the scripts; no imports. |
| `src/lib/bb6/busycoq_rules.js` | The rule for "a file proves a machine". Shared by the page and the scripts. |
| `src/lib/bb6/busycoq_live.js` | The browser's live check against the GitHub API, and the overlay it applies. |
| `src/lib/bb6/classes.js`, `table.css` | Class → wiki page map, labels; responsive card layout. |
| `static/bb6/holdouts.json`, `src/lib/bb6/summary.json` | The generated data file (and a 3-line summary for the homepage) (schema below, JSON Schema in `static/bb6/holdouts.schema.json`). |
| `static/BB6_holdouts_608.txt` | mxdys's list, one machine per line, in order. |
| `data/bb6/sources/` | One snapshot per source (inputs of the build). |
| `scripts/bb6-holdouts/` | Importers, the build (`build.mjs`, rules in `conflicts.mjs`) and the tests. |
| `.github/workflows/bb6-holdouts.yml` | Daily scheduled refresh that opens a data-update PR (see below). |

## Refreshing the data

Needs Node 20+ and, for the busycoq step, `git` and a GitHub token (`GITHUB_TOKEN`, or `gh auth login`).
No npm dependencies. Each step writes one file under `data/bb6/sources/`; `build.mjs` merges them offline.

```sh
# 1. New official list: save it as static/BB6_holdouts_<n>.txt and its equivalence groups as
#    data/bb6/sources/BB6_holdouts_<m>_eqv_<n>.txt, then edit data/bb6/sources/list.json
#    (count, published, published_by, discord links, file names). The homepage
#    count and file name follow from the data.

# 2. busycoq: verify/ files at the head of BB6, and every PR
node scripts/bb6-holdouts/fetch-busycoq.mjs            # --clone <dir> reuses a checkout of BB6

# 3. wiki pages named after a holdout
node scripts/bb6-holdouts/fetch-wiki.mjs

# 3b. (optional, maintainers only) links to the Discord messages that mention each holdout, from a local
#     copy of the server; skipped (and the last snapshot kept) when there is none
node scripts/bb6-holdouts/fetch-discord.mjs [<copy-dir>]     # or set BB6_DISCORD_COPY

# 4. (optional, when the sources change) Robin's sheet and slugbird's guide
node scripts/bb6-holdouts/import-sheet.mjs <csv-dir> <export-date> [--strikethrough <file>]
node scripts/bb6-holdouts/import-slugbird.mjs <guide.html> <url>

# 5. merge
node scripts/bb6-holdouts/build.mjs                     # writes static/bb6/holdouts.json
node scripts/bb6-holdouts/build.mjs --check             # exit 1 if the file on disk is stale
node --test scripts/bb6-holdouts/test.mjs
```

Snapshots are only rewritten when their content changed (not just `fetched_at`), so re-running a fetch when
nothing moved leaves the working tree clean.

The build is deterministic: the same inputs give the same bytes. `generated_at` is the time of the newest source
fetch, not the time of the build, so re-running it changes nothing.

## Automatic refresh

`.github/workflows/bb6-holdouts.yml` runs daily and on demand (`workflow_dispatch`): it runs steps 2 and 3, the build
and the tests, and, if `data/`, `static/bb6/` or `src/lib/bb6/summary.json` changed, pushes the branch `bot/bb6-holdouts-data` and opens (or
updates) a pull request. It needs no secrets, only the workflow's `GITHUB_TOKEN`, but the repository setting
*Settings → Actions → General → Allow GitHub Actions to create and approve pull requests* must be on. It cannot refresh
the official list, the sheet, slugbird's guide or the Discord links (those need a person); anyone can also do any
refresh by hand and open a PR with the result.

## What is used from each source

| Source | Used | Not used |
| --- | --- | --- |
| mxdys's list and equivalence groups (Discord #bb6) | machines, order, equivalent machines | — |
| RobinCodes's spreadsheet, exported 2026-10-09 | class, Results status, "simulated at least 1e13/14/15" (derived from the Direct Simulation tab), the cell each came from | free-text notes, Discord links, the user's tracker tiers/buckets/notes |
| slugbird's BB(6) Holdout Guide, 2026-11-03 | class, status tag, PR number, furthest simulation | its descriptions |
| busycoq (`BB6` branch and its PRs) | which holdouts have a proof, which PRs add one | — |
| bbchallenge wiki | existence of a page for a holdout or a class | page content |
| bbchallenge Discord (local copy of the server) | message links (channel, message id, date) for messages whose text contains the machine or an equivalent one | message text, authors, attachments. The copy only reaches back to `covers_from`. |

The sheet is keyed to the older 1534-machine list. Its machines are mapped to today's rows through the
equivalence groups; each record says whether it came from the same machine (`exact`/`mirror`) or an equivalent
one (`equivalent`). Sheet *status* is only taken from the same machine, never an equivalent one. Where sources
disagree, nothing is overwritten: both values are shown.

*Conflict or note?* A `conflicts` entry (shown with a warning) is a real disagreement: the sources give different
classes, or a source contradicts busycoq (it says solved and busycoq has no proof or open PR, or busycoq has it solved
and a source still calls it unsolved or a cryptid). A source that is merely behind or ahead of busycoq on the path
*ready → PR → solved* is not a disagreement: it goes to `notes`, which the page shows without a warning. So do slugbird's
"Reported by others" (an unverified claim) and a cryptid tag only one source has. The rules are in
`scripts/bb6-holdouts/conflicts.mjs` and tested.

The only per-machine data written by hand is `data/bb6/sources/notable.json`: names (Antihydra, Space Needle, Lucy's
Moonlight), community tags and short remarks, copied from the wiki's [BB(6) Cryptids section](https://wiki.bbchallenge.org/wiki/BB(6)#Cryptids)
and [Beaver Math Olympiad](https://wiki.bbchallenge.org/wiki/Beaver_Math_Olympiad) page, and the seven energy vampires
from [Thomas Reus's family repository](https://github.com/thomasreus-bb/bb6-vampire-family-1RB0LA_0RC0RB_1LD1LA_1LC1RE_1RF0RD_1LC---).
Each entry is keyed by a machine code and matched to its row through the equivalence groups. When the wiki changes,
edit the file to match; only use terms the community already uses.

## The busycoq rule

A holdout is **solved** when a machine code of its equivalence group (any mirror/renaming) appears in a
`verify/*.v` file (not `Eqv*.v`) that has a final theorem about it: `Theorem|Lemma|Corollary|Fact … : ~halts … c0`
(or the `halts`/`halts_in`/`halts_at_trans` form) and no `Admitted`. Files named `Eqv*.v` only say two machines are
equivalent, so they are listed as `mentioned_in` with `kind: "equivalence"`. A pull request that adds such a file
makes the holdout **pr_open** while it is open; a merged PR counts as solved (it is on the branch). Anything else
is a *mention*. This is a heuristic made by a program: it matches the 1 solved machine slugbird also reports,
but treat it as a pointer and open the linked file before relying on it.

## Live check (in the browser)

On load, `busycoq_live.js` asks the GitHub REST API (unauthenticated, 60 requests/hour per visitor IP):

1. the open and recently updated PRs (1–3 requests);
2. `git/ref/heads/BB6`; if the head moved since the snapshot, `compare/<snapshot>...<head>` (1 request);
3. `pulls/N/files` for PRs that are new or changed since the snapshot (at most 6).

It overlays the result on the snapshot (a merged PR makes holdouts solved, a closed one makes them open again) and
caches it in `localStorage` for 10 minutes. On any error, including a rate limit (403/429), it shows the snapshot and a
banner saying the live check failed. It never throws. A "check again" button forces a refresh (at most once a minute).

## `holdouts.json` format

Stable and versioned (`schema_version`, currently `1`); new optional fields may be added without a bump, anything
else bumps it. Machine-readable schema: `/bb6/holdouts.schema.json`. Machine codes are in the format of the
bbchallenge wiki: six groups of two transitions joined by `_`, halt written `---`.

Top level: `schema_version`, `generated_at`, `list`, `busycoq`, `sources`, `url_templates`, `sheet_tabs`, `counts`,
`holdouts`.

- `list`: `count`, `published` (date), `published_by`, `discord_url`, `file` (the plain list), `equivalence_file`, `equivalent_machines`.
- `busycoq`: `repo`, `branch`, `head{sha,date,message}` (the branch head the snapshot was made at), `snapshot_fetched_at`, `verify_files`, `prs_url`, `pr_snapshot[{number,state,head_sha,updated_at}]` (used by the live check).
- `sources`: `list|sheet|slugbird|busycoq|discord|wiki`, each with `name`, `url`, `as_of` (and `by`, `keyed_to_list` where relevant). Read `as_of` to judge staleness.
- `url_templates`: how to build links, with `{tm}`, `{wiki_page}`, `{number}`, `{file}`, `{tab_gid}`, `{ref}` placeholders. `sheet_tabs` maps a tab name to its gid.
- `counts`: `by_status{open,pr_open,solved}`, `with_conflicts`.

Each element of `holdouts` (one per line of the official list, in list order):

| Field | Meaning |
| --- | --- |
| `n` | 1-based position in the list; stable until the list changes |
| `tm` | The machine as it appears in the list (the representative of its group) |
| `name` | A name for a famous machine (Antihydra), else `null` |
| `tags[]` | Community tags: `Cryptid`, `Probviously halting`, `Probviously non-halting`, `Potential Cryptid`, `Energy vampire`, `BMO<n>`; the top-level `tags` gives each a link and a one-line meaning |
| `simulated_halt` | Present when an accelerated simulation found a halt that has no Rocq proof yet: `date`, `detail`, `source` (a key of `sources`) |
| `aliases[]` | The other machines in its equivalence group: `tm`, `relation` (`mirror` = mirror/renaming, `equivalent` = mxdys's equivalence) |
| `class` | The class to show: the sheet's if it has one, else slugbird's, else `null` |
| `classifications[]` | Every source's class: `source` (`sheet`\|`slugbird`), `class`, and for the sheet `cell{tab,ref}`, and `machine`+`relation` when it came from an alias |
| `sheet` | `status` (the sheet's Results status or `null`), `simulated_log10_min` (13, 14 or 15: known to run at least that many steps), `cell`; `null` if the sheet has nothing |
| `slugbird` | `status` (its tag: pr, ready, rules, reported, cryptid, pattern, lottery, little), `pr`, `simulated` (e.g. `"6.0e79"`); `null` if absent |
| `busycoq` | `status`: `open` \| `pr_open` \| `solved`; `solved_in[{file,machines?}]`; `prs[{number,title,author,state,relation,files}]` (`relation`: `proves` or `mentions`); `mentioned_in[{file,kind,machines?}]` (`kind`: `equivalence` or `no-final-theorem`) |
| `wiki_pages[]` | Wiki page titles for this holdout's machines (use `url_templates.wiki_page`) |
| `site_page` | Optional path of a page on this site (Antihydra) |
| `discord[]` | Messages mentioning the machine or an equivalent one, oldest first: `channel_id`, `channel` (name), `message` (id), `date`; link with `url_templates.discord_message`. Empty if the Discord step was never run |
| `conflicts[]` | Real disagreements: `kind` (`class`, `solved-not-in-busycoq`, `unsolved-in-source`, `cryptid`) and a sentence `detail` |
| `notes[]` | Differences that are not disagreements: `kind` (`behind`, `stale`, `ahead`, `unverified`, `one-source`) and `detail`; and remarks from the wiki or Discord, `kind` `community` (e.g. "Similar to Antihydra") |

Example: take everything still open, longest simulated first:

```sh
curl -s https://bbchallenge.org/bb6/holdouts.json |
  jq '[.holdouts[] | select(.busycoq.status != "solved")] | sort_by(-(.sheet.simulated_log10_min // 0)) | .[:10] | map({n, tm, class})'
```

Not recorded here: who is working on a machine (there are no claims yet), per-machine free-text notes, tiers or difficulty, and Discord message text.
